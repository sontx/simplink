## Proposed graph connections

- Authoring procedures produce `state.authoring.documents-exist` and `state.authoring.no-lint-errors`; CLI search, resolution, and docs export check the latter.
- Core embedding checks document existence; SDK operations share a loaded snapshot and must recreate it after changes.
- MCP startup checks document existence and reports lint status, but must not falsely require zero lint errors to start.
- UI management procedures check `state.ui.workspace-running`; UI repair and preview remain usable with lint findings.
- The planning goals offer CLI and KB-tool alternatives. MCP connection is needed only for the MCP execution path; in-process KB tools require no running MCP server.
- Every constraint will be linked only to the procedures/capabilities to which the evidence applies. No paid plans or Simplink permission tiers were found; tenant plan/permission inputs describe the loaded product KB.

## Open questions

Each answer records the evidence found. "Decision needed" marks product choices the code cannot settle.

1. **Are the end-user and SDK intents the right entry points? Keep advanced code extensions in scope?**
   - Evidence: `packages/core/README.md` has a public "Code extensions" section for sources, validation, lint, search, resolution, rendering, and tools. `packages/core/src/index.ts` exports them. They are documented public API, not internals.
   - Recommendation: keep `goal.integration.customize-kb` as one overview goal with one procedure, as planned. Keep `goal.integration.load-git-kb` separate because the core SDK supports Git sources.
   - Decided (2026-10-20): keep extensions in scope as one overview goal.

2. **Node maintenance: one goal, or a separate removal goal?**
   - Evidence: removal is a separate action. `packages/ui/src/routes/nodes/$id.tsx:299` shows "Delete file". Its confirmation (`:313`) says "{path} will be permanently deleted." and "{count} nodes reference this node. Their relationships will become dangling." The workspace service deletes the file through the folder store and rebuilds. It does not update the nodes that reference it.
   - Recommendation: split it into `goal.ui.delete-node` and `procedure.ui.delete-node`. Steps: check Incoming relationships, retarget or remove them, Delete file, then confirm Issues has no new errors. Deletion differs from create/edit from start to finish, cannot be undone in the UI, and has its own search terms ("xóa node", "delete a node"). Files in a Git checkout can be restored with Git outside the UI. `goal.ui.maintain-nodes` keeps create and edit.
   - Decided (2026-10-20): split. Rows added in the UI area.

3. **Is direct UI HTTP API integration a supported public use case?**
   - Resolved by the browser migration: the UI ships a static SPA with no server, API, or `createUiHandler` export. Workspace reads and writes run in `packages/ui/src/workspace/service.ts` and `store.ts`.

4. **Skill reference drift and the README "two packages" wording**
   - Confirmed: `SKILL.md` and `references/schema.md` still name `kb-lint`, `kb-search`, and `kb-resolve`. `schema.md` does not describe the optional `docs: { path, order }` frontmatter in `packages/core/schemas/defs.schema.json:124`. When drafting, use the bundled schemas and the `simp-*` binaries.
   - Correction: the README migration paragraph is accurate. It came from commit `b17914a` ("Split core and MCP into workspace packages"), where the former `@sontx/simplink` was replaced by exactly two packages, core and MCP.
